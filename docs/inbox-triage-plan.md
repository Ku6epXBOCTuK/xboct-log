# Inbox и триаж задач: план работ

Дополнение к `plan.md`. Расширяет его в трёх местах: появляется служебный проект
Inbox, появляется перенос задачи между проектами и появляется запрет на
переиспользование номеров задач.

## Задача

Нужно уметь быстро зафиксировать задачу, которая пока ни к какому проекту не
относится, и позже разложить её по проектам. Это GTD-поток: capture → triage.

## Решения

**Inbox это обычный проект в БД, но особый в UI.**

Причина: `tasks.project_id` объявлен `NOT NULL`, `id` задачи вычисляется как
`${prefix}-${number}`, а номер берётся из `MAX(number)+1 WHERE project_id = ?`.
Есть ограничение `UNIQUE (project_id, number)`. В SQLite NULL-значения в
уникальном индексе считаются различными, поэтому nullable `project_id`
немедленно ломает уникальность номеров: две беспроектные задачи смогут получить
один и тот же номер. Плюс формат `PREFIX-NUMBER` перестанет быть определён.

Вывод: беспроектных задач не существует, есть проект Inbox. Никакой миграции
схемы не требуется, Inbox это строка в `projects`.

**Перенос меняет `id` задачи.**

`SPA-12` после переноса в Inbox становится `INB-3`. Инвариант
`id = PREFIX-NUMBER` сохраняется, в том числе для вложенных ссылок (`epic_id`).

**Перенос это отдельная команда `moveTask`, а не поле в `TaskPatch`.**

Перенос меняет первичный ключ, то есть ответ операции это другая сущность.
Смешивать это с `updateTask`, который всегда возвращает задачу с тем же `id`,
нельзя.

**Номера задач не переиспользуются. Делается сразу, а не потом.**

Номер это `MAX(number)+1` по проекту, поэтому если задача с наибольшим номером
уходит из проекта или удаляется, потолок опускается и следующий номер выдают
заново. Для внешних ссылок вроде `fixes SPA-12` в коммитах это тихая порча
данных. Поэтому в шаг 2 входит таблица
`task_number_high_water (project_id, last_number)`, которая помнит максимальный
выданный номер и не даёт его выдать повторно.

## Шаги

Суммарно около 5.5 часов.

### Шаг 1. Inbox как зарезервированный проект (45 мин)

1. `src/lib/types.ts` — экспорт `INBOX_PROJECT_ID = "inbox"` и
   `INBOX_PROJECT_PREFIX = "INB"`. Файл чистый, его можно импортировать из UI.
2. `src/lib/server/projects.ts` — `ensureInbox(db)`: вставка строки
   `{ id: "inbox", name: "Inbox", prefix: "INB" }` по принципу «если нет».
   Порядок проверок обязателен: сначала ранний выход, если проект с `id` равным
   `"inbox"` уже есть, и только потом проверка префикса. Иначе на втором запуске
   функция будет падать сама на себе. Если префикс `INB` занят проектом с другим
   `id`, падать с внятным сообщением на старте и с именем этого проекта, потому
   что сырое `UNIQUE constraint failed: projects.prefix` ничего не объясняет.
   Если Inbox существует и почему-то архивирован, сбросить `archived_at` в
   `NULL`, иначе UI его спрячет и захват задач перестанет работать.
3. `src/lib/server/projects.ts` — `updateProject` отклоняет `archived: true` для
   `id === "inbox"`.
4. `src/hooks.server.ts` — в `init()` рядом с `startBackupScheduler()` вызвать
   `ensureInbox(getDb())`.

Ограничение: `ensureInbox` нельзя вызывать внутри `openDatabase`. В
`src/lib/server/app.spec.ts` есть проверки вида
`listProjects(db)).toHaveLength(0)`, сид внутри `openDatabase` их сломает.
`app.spec.ts` при этом не переписываем.

### Шаг 2. Невосстановимые номера задач (45 мин)

1. `src/lib/server/db.ts` — в `SCHEMA` добавить таблицу
   `task_number_high_water (project_id TEXT PRIMARY KEY REFERENCES projects (id), last_number INTEGER NOT NULL)`.
   Создаётся тем же `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE` не нужен,
   механизм миграций в `db.ts` отсутствует.
2. `src/lib/server/tasks.ts` — `allocateNumber(db, projectId)`: берёт
   `MAX(COALESCE(last_number, 0), COALESCE(MAX(number) по проекту, 0)) + 1`,
   поднимает `last_number` через
   `INSERT ... ON CONFLICT (project_id) DO UPDATE`. `MAX(number)` остаётся в
   формуле, поэтому бэкфилл для существующих баз не нужен.
3. `createTask` переходит с inline `MAX(number)+1` на `allocateNumber`, внутри
   уже открытой транзакции. `deleteTask` таблицу не трогает, в этом и смысл.

### Шаг 3. `moveTask` на сервере (1 ч)

1. `src/lib/server/tasks.ts` — `moveTask(db, id, projectId)`. 404, если задача
   не найдена. 404, если целевой проект не найден. Если проект совпадает с
   текущим, возвращаем задачу без изменений.
2. Внутри `BEGIN IMMEDIATE` переносится всё поддерево.
   `collectSubtree(db, rootId)` собирает корень и всех потомков (обход по
   `epic_id`, порядок детей — по старому `number`). Каждому узлу
   `allocateNumber` целевого проекта выдаёт новый `number`, новый `id` это
   `prefix-number`. Затем узлы пишутся одним проходом
   `UPDATE ... SET id, project_id, number, epic_id, updated_at`, где `epic_id`
   перепривязан к новому `id` родителя из той же пачки. Корень, чей родитель
   остался в старом проекте, получает `epic_id = NULL`.
3. Внутри той же транзакции нужен `PRAGMA defer_foreign_keys = ON`. Ограничение
   `epic_id REFERENCES tasks(id)` объявлено без `ON UPDATE CASCADE`, а внешние
   ключи проверяются немедленно, поэтому смена `id` родителя при живых детях
   падает, и дети, указывающие на ещё не существующий `newId`, падают тоже.
   Отложенная проверка снимает это, ключи валидируются на `COMMIT`. Здесь нужен
   один комментарий `// NOTE:` — причина неочевидна.
4. Переносится именно поддерево, а не один эпик: `epic_id` требует, чтобы эпик
   был в том же проекте (это проверяет `validateEpic`), поэтому оставить детей в
   старом проекте нельзя — получится ссылка через границу проекта. Если
   переносимая задача была ребёнком эпика, её `epic_id` очищается: в новой пачке
   родителя нет. Если переносимая задача сама эпик, дети переезжают вместе с ней
   и сохраняют ссылку на её новый `id`.
5. `src/lib/remote/tasks.remote.ts` —
   `moveTask = command(z.object({ id: z.string().min(1), project_id: z.string().min(1) }), ...)`.
   В `TaskPatch` поле `project_id` не добавляется.

### Шаг 4. Перенос из карточки задачи (45 мин)

1. `src/lib/components/Selected.svelte` — селект `Project`, новые пропы
   `projects` и `onmove(oldId, task)`. По `change` вызывается `moveTask`,
   `selected` заменяется перенесённой задачей, вызывается `onmove`.
2. `src/routes/+page.svelte` — `applyUpdate` ищет задачу по `id` (строка 150,
   `task.id === updated.id`), а при переносе `id` меняется, поэтому старая
   запись останется, а новая не появится. Добавить отдельный проп
   `onmove(oldId, task)` и менять запись по старому `id`, не трогая логику
   `applyUpdate`.
3. `src/routes/+page.svelte` — передать `projects` в `<Selected>`.

### Шаг 5. Capture и закрепление Inbox (30 мин)

1. `src/lib/components/NewTask.svelte` — в `reset()` подставлять
   `INBOX_PROJECT_ID` вместо `projects[0]?.id`, Inbox идёт первым пунктом
   селекта. Захват задачи сводится к заголовку и Enter.
2. `src/lib/server/projects.ts` — `listProjects` сортирует Inbox первым через
   `CASE WHEN id = ? THEN 0 ELSE 1 END, name`.
3. `src/lib/components/layout/SideBar.svelte` — скрыть кнопку архивации для
   `id === "inbox"`.

### Шаг 6. Настоящий фильтр по проекту (1 ч)

`activeProject` в `SideBar.svelte` сейчас чисто визуальный, `+page.svelte` по
проекту не фильтрует. Без этого «показать только Inbox» не работает и триаж не
собирается в процесс.

1. Поднять состояние выбранного проекта в `+page.svelte`.
2. Добавить фильтр по `project_id` в `visibleTasks`.
3. Синхронизировать состояние с URL.

### Шаг 7. Тесты (45 мин)

`src/lib/server/app.spec.ts`, новые кейсы:

1. Перенос выдаёт следующий номер целевого проекта.
2. Ребёнок эпика отвязывается при переносе в другой проект.
3. Дети эпика переезжают вместе с ним и сохраняют ссылку на новый `id`.
4. Перенос в тот же проект ничего не меняет.
5. 404 по неизвестной задаче и по неизвестному проекту.

Отдельно по номерам:

1. После удаления задачи с максимальным номером следующий номер в проекте
   больше, а не тот же самый.
2. После переноса задачи с максимальным номером следующий номер в исходном
   проекте больше, а не тот же самый.
3. Номер не выдаётся повторно в проекте, в который задача была перенесена.

## Ссылки на задачи

Сейчас единственная ссылка на `id` задачи это `epic_id`, и она обрабатывается в
шаге 3. Проблема появится, когда ссылки уйдут наружу: git export с
`fixes SPA-12` в коммитах, VS Code extension, импорт из старого `~/backlog`,
агентская интеграция. Это пункты из разделов 2 и 10 `plan.md`, то есть не
сегодня.

Что зафиксировано сейчас:

**1. Перенос обязан быть единственной точкой переписывания `id`.** Никакой
другой код не меняет `id` задачи. Тогда добавление таблицы алиасов позже будет
вставкой одной строки в одну функцию.

**2. Номера задач больше не переиспользуются.** Решено делать сразу, разбор
причины в разделе «Решения», реализация в шаге 2. Это закрывает тихий сценарий,
в котором внешняя ссылка на `SPA-5` через месяц указывала бы на совсем другую
задачу.

**3. Таблица алиасов не нужна в v1.** Когда появятся внешние ссылки, добавляется
`task_aliases (alias TEXT PRIMARY KEY, task_id TEXT NOT NULL REFERENCES tasks(id))`,
`moveTask` пишет в неё старый `id`, и появляется `resolveTaskRef(db, ref)` для
границы импорта и экспорта. Оценка 1 ч. Сейчас это преждевременно, потому что
внешних ссылок нет.

## Вне области работ

1. Быстрый перенос прямо из строки таблицы. Карточки достаточно.
2. Массовый перенос нескольких задач.
3. Правило «Inbox не может быть эпиком».
4. Автотриаж и напоминания о задачах, залежавшихся в Inbox.
5. Обратный поиск по алиасам, резолвер появится вместе с первой внешней ссылкой.

## Критерии готовности

1. Задача создаётся в Inbox за одно нажатие Enter из формы создания.
2. Inbox виден первым в сайдбаре и его нельзя архивировать.
3. Карточка задачи позволяет сменить проект, после чего `id` меняется, панель
   остаётся открытой на новой задаче.
4. Ссылка «показать только Inbox» работает и таблица фильтруется по проекту.
5. Номера задач не переиспользуются после переноса и после удаления.
6. `pnpm test` и `pnpm check` проходят.
