# Спецификация проекта: локальный бэклог задач

## 1. Что это

Локальный сервер + веб-интерфейс для ведения личного бэклога задач по нескольким
проектам. Задачи хранятся на сервере, доступны через браузер, всегда под рукой.
Один пользователь, одна машина.

## 2. Что НЕ входит в первую версию

Явно, чтобы не расползалось:

- Интеграция с ИИ-агентами (hooks, skills, автоматические проверки).
- Экспорт в git.
- VS Code-расширение.
- Многопользовательский режим, аутентификация, права.
- Синхронизация с облаком.
- Уведомления, напоминания, календарь.
- Статистика по токенам, стоимости, «эффекту».
- Автоматическое закрытие задач, автоматические эпики.
- Retention (удаление старых задач).
- Импорт из старого `~/backlog` (можно позже, отдельной задачей).

Всё это — потенциальные расширения, но не фундамент.

## 3. Основные понятия

**Проект** — группа задач. Имеет короткий идентификатор (например, `spa`),
название, префикс для ID задач (например, `SPA`). Проектов может быть много.

**Задача** — единица работы. Принадлежит одному проекту. Имеет:

- уникальный ID вида `SPA-12` (префикс проекта + номер);
- заголовок (одна строка);
- описание (многострочный текст, markdown);
- статус;
- приоритет;
- опциональные теги;
- опциональную ссылку на код (`source`: файл + строка);
- опциональную связь с эпиком;
- дату создания и дату последнего изменения.

**Статусы:** `open`, `in-progress`, `blocked`, `done`, `cancelled`.

**Приоритеты:** `low`, `medium`, `high`, `critical`.

**Эпик** — задача, которая группирует другие задачи. Отдельная сущность не
нужна: это та же задача с признаком «эпик». Задачи могут ссылаться на эпик.

## 4. Модель данных

### 4.1. `projects`

| Поле          | Тип                 | Назначение                             |
| ------------- | ------------------- | -------------------------------------- |
| `id`          | строка, PK          | короткий идентификатор, например `spa` |
| `name`        | строка              | отображаемое название                  |
| `prefix`      | строка              | префикс для ID задач, например `SPA`   |
| `created_at`  | timestamp           | когда создан                           |
| `archived_at` | timestamp, nullable | если проект больше не активен          |

**Зачем:** разделять задачи по проектам. Без проектов все задачи свалятся в одну
кучу, и фильтровать станет невозможно.

**Правила:**

- `id` уникален, состоит из латиницы/цифр/дефиса.
- `prefix` уникален (иначе ID задач пересекутся).
- Удаление проекта не предусмотрено в первой версии — только архивация.

### 4.2. `tasks`

| Поле          | Тип                     | Назначение                                                |
| ------------- | ----------------------- | --------------------------------------------------------- |
| `id`          | строка, PK              | например `SPA-12`                                         |
| `project_id`  | FK → projects.id        | к какому проекту относится                                |
| `number`      | целое                   | номер внутри проекта, для генерации ID                    |
| `title`       | строка                  | короткий заголовок                                        |
| `description` | текст                   | подробное описание, markdown                              |
| `status`      | enum                    | `open` / `in-progress` / `blocked` / `done` / `cancelled` |
| `priority`    | enum                    | `low` / `medium` / `high` / `critical`                    |
| `is_epic`     | boolean                 | это эпик или обычная задача                               |
| `epic_id`     | FK → tasks.id, nullable | если задача входит в эпик                                 |
| `source_file` | строка, nullable        | путь к файлу кода                                         |
| `source_line` | целое, nullable         | номер строки                                              |
| `tags`        | массив строк            | произвольные метки                                        |
| `created_at`  | timestamp               | когда создана                                             |
| `updated_at`  | timestamp               | последнее изменение                                       |
| `closed_at`   | timestamp, nullable     | когда закрыта                                             |

**Зачем каждое поле:**

- `number` отдельно от `id` — чтобы можно было генерировать следующий номер
  атомарно, не парся строки.
- `description` — потому что заголовка мало для «что сломается и почему».
- `source_file` / `source_line` — чтобы в будущем прыгать к коду; в браузере
  просто показывается.
- `tags` — гибкие метки без заведения отдельных сущностей.
- `epic_id` — связь, а не иерархия. Задача может быть без эпика.
- `closed_at` — чтобы отличать «закрыта давно» от «закрыта только что», если
  понадобится.

**Индексы:**

- по `project_id` (фильтр по проекту);
- по `status` (фильтр по открытым);
- по `updated_at` (сортировка «недавно менявшиеся»);
- по `epic_id` (задачи эпика).

**Правила:**

- `id` генерируется как `<prefix>-<number>`, `number` увеличивается на 1 в
  рамках проекта.
- `epic_id` может ссылаться только на задачу с `is_epic = true` в том же
  проекте.
- Задача не может быть эпиком для самой себя.
- `source_line` без `source_file` не имеет смысла — валидировать.

## 5. API сервера

REST поверх JSON. Все ответы — JSON. Ошибки — с HTTP-кодом и телом
`{ error: "..." }`.

### 5.1. Проекты

**`GET /api/projects`** — список проектов. Зачем: выпадающий список при создании
задачи, страница «все проекты».

**`POST /api/projects`** — создать проект. Тело: `{ id, name, prefix }`. Зачем:
без проекта нельзя создать задачу.

**`GET /api/projects/:id`** — проект + счётчики задач по статусам. Зачем:
карточка проекта в UI.

**`PATCH /api/projects/:id`** — переименовать, архивировать. Зачем: исправить
опечатку, убрать неактуальный проект из списков.

### 5.2. Задачи

**`GET /api/tasks`** — список задач с фильтрами. Query-параметры:

- `project` — ID проекта (или `all`);
- `status` — один или несколько, через запятую;
- `priority` — один или несколько;
- `tag` — один или несколько;
- `epic` — ID эпика;
- `q` — текстовый поиск по заголовку и описанию;
- `sort` — `updated_at` / `created_at` / `priority`;
- `limit`, `offset` — пагинация.

Зачем: это основной эндпоинт UI. Список задач, фильтры, поиск.

**`POST /api/tasks`** — создать задачу. Тело:
`{ project_id, title, description?, priority?, tags?, source_file?, source_line?, epic_id?, is_epic? }`.
Ответ: созданная задача с присвоенным ID. Зачем: основное действие. Должно быть
быстрым и не требовать лишних полей.

**`GET /api/tasks/:id`** — одна задача со всеми полями. Зачем: карточка задачи.

**`PATCH /api/tasks/:id`** — изменить поля. Тело: любые из
`{ title, description, status, priority, tags, source_file, source_line, epic_id }`.
Зачем: смена статуса, правка текста, приоритет — всё через один эндпоинт.

**`POST /api/tasks/:id/close`** — закрыть задачу. Тело:
`{ as: "fixed" | "obsolete" | "duplicate", reason?: "..." }`. Зачем: отдельный
эндпоинт, потому что закрытие — это не просто смена статуса, а осмысленное
действие с причиной. В первой версии причину можно не хранить, но интерфейс
заложить.

**`DELETE /api/tasks/:id`** — удалить задачу. Зачем: ошибочно созданную задачу
надо как-то убрать. Альтернатива — статус `cancelled`, но для «создал не то»
удаление честнее.

### 5.3. Эпики

Эпики — это задачи с `is_epic = true`. Отдельные эндпоинты не нужны, кроме:

**`GET /api/epics`** — список эпиков (задачи с `is_epic = true`), опционально по
проекту. Зачем: выпадающий список при привязке задачи к эпику.

### 5.4. Служебное

**`GET /api/health`** — `{ ok: true }`. Зачем: проверка, что сервер жив, для UI
и для автозапуска.

## 6. Веб-интерфейс

Одна страница или несколько — на ваше усмотрение. Важно, чтобы:

### 6.1. Список задач (главный экран)

- Таблица или список карточек.
- Колонки: ID, заголовок, проект, статус, приоритет, теги, обновлено.
- Фильтры сверху: проект, статус, приоритет, тег, поиск.
- Сортировка по клику на заголовок колонки.
- Клик по задаче → открывается карточка.
- Кнопка «Новая задача».

**Зачем:** это экран, который «всегда перед глазами». Он должен открываться
мгновенно и не требовать лишних кликов.

### 6.2. Карточка задачи

- Все поля, редактируемые на месте (inline) или через форму.
- Смена статуса — кнопками или выпадающим списком, одно действие.
- Смена приоритета — так же.
- Теги — добавление/удаление.
- Связь с эпиком — выпадающий список эпиков проекта.
- `source` — поля файл и строка.
- Кнопка «Закрыть» с выбором причины.
- Кнопка «Удалить» с подтверждением.

**Зачем:** здесь происходит 90% работы. Каждое действие — один клик, без
«сохранить».

### 6.3. Создание задачи

- Модальное окно или отдельная страница.
- Поля: проект (обязательно), заголовок (обязательно), описание, приоритет (по
  умолчанию `medium`), теги, source, эпик.
- Enter в заголовке — создать и открыть карточку.
- Возможность создать ещё одну подряд, не закрывая окно.

**Зачем:** создание должно быть быстрым. Если это 5 кликов — вы не будете это
делать.

### 6.4. Проекты

- Список проектов со счётчиками задач.
- Создание проекта.
- Архивация.

**Зачем:** раз задачи по проектам, нужен способ управлять проектами.

### 6.5. Общие требования к UI

- Всё работает без перезагрузки страницы (обновление через API).
- URL отражает состояние: `/tasks?project=spa&status=open` — можно сохранить в
  закладки.
- Никаких модальных окон там, где хватит inline-редактирования.
- Тёмная/светлая тема — по системной.

## 7. Порядок реализации

Каждый шаг — рабочий результат, который можно потрогать.

### Шаг 1. Хранилище и модель

**Что:** таблицы `projects` и `tasks`, операции чтения/записи, генерация ID.

**Зачем:** без этого нечего показывать. Хранилище — фундамент, и его стоит
зафиксировать раньше, чем API и UI.

**Проверка:** можно создать проект и задачу программно, прочитать их обратно.

### Шаг 2. API: проекты и задачи

**Что:** эндпоинты из раздела 5, кроме `close` и `epics`.

**Зачем:** API — контракт между сервером и UI. Пока он не готов, UI писать не на
что.

**Проверка:** через `curl` или любой HTTP-клиент создаётся проект, создаётся
задача, меняется статус, читается список с фильтрами.

### Шаг 3. UI: список задач

**Что:** главный экран с таблицей, фильтрами, сортировкой. Без редактирования.

**Зачем:** это то, что «всегда перед глазами». Если список неудобен, остальное
не спасёт.

**Проверка:** открывается браузер, видно все задачи, фильтры работают.

### Шаг 4. UI: карточка задачи и редактирование

**Что:** открытие карточки, inline-редактирование всех полей, смена статуса и
приоритета.

**Зачем:** здесь происходит основная работа. Без этого UI бесполезен.

**Проверка:** можно поменять статус, приоритет, описание — и это сохраняется.

### Шаг 5. UI: создание задачи

**Что:** форма создания, привязка к проекту, теги, source, эпик.

**Зачем:** без создания UI — только читалка.

**Проверка:** создаётся задача, она появляется в списке.

### Шаг 6. Эпики

**Что:** `is_epic`, `epic_id`, эндпоинт `GET /api/epics`, UI для привязки и
просмотра задач эпика.

**Зачем:** когда задач станет много, группировка понадобится. Раньше —
преждевременно.

**Проверка:** создаётся эпик, в него привязываются задачи, видно список.

### Шаг 7. Управление проектами

**Что:** UI для создания, переименования, архивации проектов.

**Зачем:** пока проектов мало, можно создавать их через API. Но когда их станет
несколько — нужен UI.

**Проверка:** создаётся проект, задачи привязываются к нему.

### Шаг 8. Закрытие и удаление задач

**Что:** `POST /api/tasks/:id/close`, `DELETE /api/tasks/:id`, UI для этого.

**Зачем:** задачи надо закрывать. В первой версии можно было бы просто менять
статус, но отдельное действие с причиной — это то, что отличает бэклог от
списка.

**Проверка:** задача закрывается, исчезает из «открытых», появляется в
«закрытых».

### Шаг 9. Автозапуск сервера

**Что:** сервис, который поднимает сервер при входе в систему.

**Зачем:** чтобы не запускать вручную. Без этого «всегда перед глазами» не
работает.

**Проверка:** после перезагрузки сервер доступен.

## 8. Что решить до начала

Эти решения влияют на всё, и их лучше принять сейчас:

**1. Где хранится состояние.** Один файл БД в `~/.backlog/` или рядом с
проектом? Я бы — в `~/.backlog/`, чтобы не зависеть от текущей директории.

**2. Порт.** По умолчанию `4317` (как в оригинале) или другой? Если порт занят —
падать или искать свободный? Я бы — падать с понятной ошибкой.

**3. Формат ID.** `SPA-12` (с префиксом) или просто числа? Префикс удобнее,
когда несколько проектов.

**4. Что делать при удалении проекта.** В первой версии — только архивация.
Удаление с задачами — позже, с подтверждением.

**5. Нужна ли пагинация в первой версии.** Если задач < 500, можно отдавать всё
и фильтровать на клиенте. Если больше — серверная. Я бы заложила серверную с
`limit`/`offset`, но UI сначала использовала `limit=1000`.

**6. Как UI узнаёт об изменениях.** Polling раз в N секунд или WebSocket? Для
одного пользователя polling раз в 3-5 секунд достаточно и проще. WebSocket —
если хочется мгновенности.

**7. Валидация на клиенте или сервере.** На сервере — обязательно. На клиенте —
для UX. Дублирование допустимо.

## 9. Критерии готовности первой версии

- Сервер запускается одной командой.
- В браузере открывается UI.
- Можно создать проект.
- Можно создать задачу с заголовком, описанием, приоритетом, тегами.
- Можно отфильтровать задачи по проекту, статусу, приоритету, тегу.
- Можно найти задачу по тексту.
- Можно открыть карточку и поменять любое поле.
- Можно поменять статус одним действием.
- Можно закрыть задачу.
- Всё сохраняется и переживает перезапуск сервера.
- Сервер поднимается автоматически при входе в систему.

Всё, что за пределами этого списка — не первая версия.

## 10. Что можно добавить потом (не сейчас)

Список, чтобы не забыть, но и не делать сразу:

- Экспорт в git (отдельный репозиторий, коммит на изменение).
- Импорт из старого `~/backlog` формата.
- VS Code-расширение (webview + «создать из выделения»).
- История изменений задачи (timeline).
- Статистика: сколько закрыто за период, распределение по проектам.
- Напоминания о задачах, которые давно в `in-progress`.
- Клавиатурные шорткаты в UI.
- Быстрый поиск (Cmd+K).
- Теги как отдельная сущность с цветами.
- Связи между задачами (`blocks`, `related`).
- Полнотекстовый поиск по описаниям.
- Тёмная тема с ручным переключением.
- Мобильная вёрстка (если захочется смотреть с телефона).
