# Архитектура

Бэкенд написан на Rust. Внешний контракт и типы для фронтенда выводятся из
Rust-кода. Актуальные счётчики инструментов и сценариев живут в `tools/list` и
e2e, а статус работ — в XBOCT-log; этот документ описывает только устройство
системы.

## Источники истины

1. Тип существует ровно в одном месте — в Rust. В TypeScript попадает только
   сгенерированное, руками написанных DTO и путей API нет.
2. Всё, что можно вывести из исходников (схемы, роуты, описания инструментов,
   события), выводится из них, а не дублируется.
3. Идиоматичный код: newtype'ы вместо сырых `String`/`i64`, `thiserror`-enum
   вместо строковых ошибок, владение без `clone()` ради компилятора.
4. Имена операций объявлены один раз в `OpName` (`crates/core/src/op_name.rs`).
   `Op::NAME` берёт значение оттуда, `activity_list` публикует enum, схема не
   может разойтись с Dispatch.

## Крейты

```txt
crates/core     домен, newtype'ы, ошибки, DTO, sqlx-репозитории, миграции,
                медиа, бэкапы, ретенция, планировщик
crates/ops      реестр операций: имя, вид, вход, выход, обработчик
crates/server   axum, REST, SSE, MCP, OpenAPI, отдача SPA с диска
crates/cli      лаунчер и админ-команды
```

`core` не знает про axum и MCP. Трейты нужны только там, где требуется подмена в
тестах; репозитории — функции над пулом или транзакцией.

## Операции

Один трейт описывает имя, вид, вход, выход и обработчик. Из списка `ops![]`
генерируются REST-маршруты `POST /api/<name>`, MCP-инструменты, запись
активности и выбор SSE-сущности. Добавление операции — одна строка, HTTP и MCP
не могут разъехаться.

Схемы MCP и OpenAPI строятся из тех же типов, что и код: `#[derive(JsonSchema)]`
на DTO и входах операций, описания задаются в `#[schemars(description)]`.
`$defs` собираются в `components.schemas` при публикации.

## Внешняя поверхность

| Поверхность                          | Что именно                                                                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/mcp`                               | инструменты и ресурсы, описания, input/output JSON Schema, инструкции сервера, `isError` + `structuredContent.error`, уведомления `resources/list_changed` |
| `/api/health`                        | `{ok, app, version, data?}`                                                                                                                                |
| `/api/events`                        | SSE: `sync`, `change`, `reset`, heartbeat, заголовки против буферизации                                                                                    |
| `/api/backup`                        | `{ok, path}` / `500 {ok:false, error}`                                                                                                                     |
| `/media/{id}`, `/deleted/media/{id}` | байты вложения, коды ответов                                                                                                                               |
| Ошибки                               | `{kind, message}` и статусы 400/404/409/500; подсказка `Did you mean: a -> b?`                                                                             |

## Инструменты MCP в Code Mode

Уровни задаются флагом `LAZY` в реестре операций: 18 повседневных инструментов
отдают полное описание и схемы в `tools/list`, остальные — первое предложение,
пустую схему и подсказку про `xboct_log_tool_description`. Имена всех
инструментов, их назначение и аргументы повседневных генерируются в
`INSTRUCTIONS` из `OpInfo` и JSON Schema — этот текст всегда попадает в контекст
клиента, даже когда каталог Code Mode урезан.

Code Mode показывает лишь часть каталога, поэтому в инструкциях есть прямой
вызов `tools["XBOCT-log"].<name>({...})` и откат на `search({query: '<name>'})`.
`xboct_log_tool_description` по точному имени возвращает только этот инструмент,
по словам — до восьми совпадений. `xboct_log_call` нужен только для редких
инструментов и проходит тот же dispatch.

## Типы для фронтенда

```txt
core/ops DTO  ──▶  openapi.json  ──openapi-typescript──▶  src/lib/api/schema.d.ts
                                                           └─▶ openapi-fetch
```

`src/lib/api/client.ts` — `openapi-fetch` с таймаутом, заголовком
`x-xboct-client` и `ApiError {status, kind, message}`. Обёртки в `src/lib/api/`
повторяют имена прежних remote-функций, поэтому сторы и компоненты не были
переписаны. `pnpm contract:generate` вызывается автоматически перед `check`,
`build` и `dev`, поэтому `schema.d.ts` не хранится в репозитории и не может
разойтись с реестром операций.

## База

`sqlx` с SQLite-пулом. На каждой коннекции включаются `journal_mode=WAL`,
`foreign_keys=ON` и `busy_timeout`. Пишущие транзакции идут через guard `Tx`
(`BEGIN IMMEDIATE`), иначе параллельная запись даёт `SQLITE_BUSY_SNAPSHOT`.

`ULOWER` живёт в одном модуле `core::db::ulower`, регистрируется в
`after_connect` каждой коннекции. `unsafe` есть только в этом модуле, остальные
крейты под `#![forbid(unsafe_code)]`.

Миграции лежат в `crates/core/migrations`: `0001_init.sql` — свёрнутая схема
node вместе с 26 историческими именами, `0002_request_log.sql` — журнал
запросов, `0003_plans.sql` — планы, пункты, документы, связи и ревизии текстов,
`0004_plan_keys.sql` и `0005_document_keys.sql` переключают ключи на новые
форматы. Node-база без `_sqlx_migrations` помечается применённой по контрольной
сумме первой миграции, после чего обычный мигратор применяет остальные.

## Newtype'ы

Идентификаторы и значения с ограничениями описаны newtype'ами: `ProjectId`,
`TagName`, `TaskKey`, `DocumentKey`, `Prefix`, `AttachmentId`, `ScopeId`, `Seq`.
Enum'ы DTO сериализуются через `serde`; имена задаются у соответствующего типа.

## Планы и документы

План — глобальная сущность без `project_id`; имя плана не уникально. Пункт плана
хранит внутренний id задачи, а отображаемый ключ `PREFIX-NNN` берётся JOIN'ом к
`tasks.key`: перенос задачи меняет только ключ в выводе. Позиции, заметки и
связи с документами при переносе не меняются.

Документ принадлежит проекту и имеет свой ключ `PREFIX-DOC-NNN` (например,
`BRUL-DOC-1`), `kind`, статус и историю правок в `text_revisions`. Новый парсер
`DocumentKey` принимает только три сегмента с маркером `DOC`, поэтому ключ
документа не может совпасть с ключом задачи `PREFIX-NNN`: неверный вызов
инструмента заканчивается `not_found`, а не молчаливой правкой другой сущности.
План может ссылаться на документ любого проекта. `source_file` — только
провенанс, не ключ для повторного импорта.
