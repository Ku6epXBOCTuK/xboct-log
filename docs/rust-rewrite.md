# Переписывание бэкенда на Rust

Бэкенд переписывается как **точный порт**: внешняя граница и файл базы остаются
такими же, как у node-версии. Изменения поведения, схемы и контрактов — только
отдельными задачами после переезда.

Три решения зафиксированы:

1. Фронтенд переезжает с SvelteKit remote-функций на REST + типы, сгенерированные
   из Rust.
2. Доступ к БД — `sqlx`; `ULOWER` регистрируется на коннекциях через сырой
   хендл, схема базы не меняется.
3. Деплой — только Windows-инстансы (NSSM и portable), без VPS, systemd и Caddy.

## Правила работы

1. Тип существует ровно в одном месте — в Rust. В TypeScript попадает только
   сгенерированное, руками написанных DTO и путей API нет.
2. Всё, что можно вывести из исходников бэкенда (схемы, роуты, описания
   инструментов, типы событий), выводится из них, а не дублируется.
3. Идиоматичный код: newtype'ы вместо сырых `String`/`i64`, `thiserror`-enum
   вместо строковых ошибок, владение без `clone()` ради компилятора.
4. Если паритет и идиоматичность конфликтуют — выигрывает паритет, а расхождение
   сразу уходит задачей в XBOCT-log с файлом и способом увидеть разницу. Маркеров
   в коде не остаётся: трекер и есть запись.
5. Отхождения от rust-way — места, где ради паритета код написан неидиоматично, —
   собираются задачами в эпике `LOG-312` «Отхождения от rust-way» проекта XBOCT-Log.
   Эпик разбирается после перевода Rust в продакшен: тогда паритет перестаёт быть
   обязательным и каждое отхождение снимается отдельной задачей.

## Что считается внешним контрактом

Копируется байт в байт:

| Поверхность                          | Что именно                                                                                                                                                     |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/mcp`                               | 53 инструмента, 2 ресурса, описания, input/output JSON Schema, инструкции сервера, `isError` + `structuredContent.error`, уведомления `resources/list_changed` |
| `/api/health`                        | `{ok, app, version, data?}`                                                                                                                                    |
| `/api/events`                        | SSE: `sync`, `change`, `reset`, heartbeat 15 с, заголовки `no-cache, no-transform`, `x-accel-buffering: no`                                                    |
| `/api/backup`                        | `{ok, path}` / `500 {ok:false, error}`                                                                                                                         |
| `/media/{id}`, `/deleted/media/{id}` | байты вложения, коды ответов                                                                                                                                   |
| Ошибки                               | `{kind, message}` и статусы 400/404/409/500; подсказка `Did you mean: a -> b?`                                                                                 |
| Файл БД                              | схема без новых колонок, `WAL`, `foreign_keys`, `BEGIN IMMEDIATE`, `schema_migrations`; единственная добавка — служебная `_sqlx_migrations`                    |

SvelteKit remote-функции — внутренний RPC между SPA и сервером, а не внешний
контракт. Их формат не воспроизводится: SPA переходит на REST-клиент, а всё
перечисленное выше остаётся неизменным.

## Крейты

```txt
crates/core     домен, newtype'ы, ошибки, DTO-представления, sqlx-репозитории,
                миграции, медиа, бэкапы, ретенция, планировщик
crates/ops      реестр операций: имя, вид, вход, выход, обработчик
crates/server   axum, REST, SSE, MCP, OpenAPI, встроенная SPA
crates/cli      лаунчер и админ-команды
```

`core` не знает про axum и MCP. Трейты вводятся только там, где нужна подмена в
тестах (`Clock`, `BlobStore`); репозитории — свободные функции над `&SqlitePool`,
это дешевле и честнее, чем трейт на каждую таблицу.

Newtype'ы: `TaskId`, `TaskKey` (`PREFIX-N`, парсинг и валидация в конструкторе),
`ProjectId`, `ScopeId`, `AttachmentId`, `Prefix`, `TagName`, `Seq`.
Enum'ы — `#[derive(sqlx::Type)]` с `rename_all = "kebab-case"`: `Status`,
`Priority`, `ClosedReason`, `Estimate`, `EntityKind`, `ActivitySource`,
`AppErrorKind`.

## Один источник операций

Сейчас у операции три описания: `define.ts`, MCP-регистрация в `+server.ts` и
Zod-контракт. В Rust остаётся одно:

```rust
trait Op {
    const NAME: &'static str;
    const KIND: Kind;              // Query | Command
    const MCP: bool;               // false — операция скрыта от MCP
    type Input: Deserialize + JsonSchema + ToSchema + Send;
    type Output: Serialize + JsonSchema + ToSchema + Send;

    fn description() -> &'static str;
    fn entity() -> Option<Entity>; // для SSE, None у query
    async fn run(ctx: &Ctx, input: Self::Input) -> Result<Self::Output, AppError>;
}
```

Из списка `ops![tasks_list, tasks_create, …]` макрос генерирует `enum AnyOp`,
диспетчеризацию по имени, регистрацию REST-роутов, список MCP-инструментов,
запись активности и выбор SSE-сущности. Добавление операции — одна строка, и она
не может разъехаться между HTTP и MCP.

## Типы для фронтенда

```txt
core/ops DTO  ──utoipa──▶  openapi.json (коммитится)  ──openapi-typescript──▶  src/lib/api/schema.d.ts
                                                                              └─▶ openapi-fetch
```

- `src/lib/remote` удаляется; типы и пути API фронт берёт только из
  `schema.d.ts`. Дрейф ловится командой `pnpm contract:check`, которая
  перегенерирует файлы и падает на `git diff --exit-code`.
- MCP-схемы не дублируются с HTTP: то же DTO с `schemars::JsonSchema` уходит в
  `rmcp`. Там, где вход MCP отличается от входа UI (`mcpInput`, `mcpNormalize`),
  это отдельный тип с явным `From`, а не приведение любой ценой.
- События SSE описаны теми же `Serialize + ToSchema` структурами, что и
  `change` в ответах.

## База данных

`sqlx` с SQLite-пулом, на каждой коннекции: `journal_mode=WAL`,
`foreign_keys=ON`, `busy_timeout`. Динамический фильтр задач — `QueryBuilder`.

Транзакции: `sqlx` открывает `DEFERRED`, node — `BEGIN IMMEDIATE`. Оставляем
`IMMEDIATE` через guard-структуру `Tx` (явный `BEGIN IMMEDIATE`, откат в `Drop`).
Иначе на параллельной записи получим `SQLITE_BUSY_SNAPSHOT` там, где node
спокойно ждал.

### `ULOWER`

Функция регистрируется в SQLite на каждой коннекции пула — так же, как это делает
node через `db.function()`:

1. `Db` владеет пулом и держит поле приватным, поэтому коннекцию нельзя получить
   в обход пула.
2. В `after_connect` каждой новой коннекции берётся сырой хендл
   (`conn.lock_handle().await?`) и на нём вызывается `sqlite3_create_function_v2`
   с флагами `SQLITE_UTF8 | SQLITE_DETERMINISTIC`.
3. Поведение повторяет node дословно: значение приводится к строке и переводится
   в нижний регистр, `null` становится `"null"`.

SQL остаётся тем же, что в node, во всех 12 местах: `ULOWER(tasks.title) LIKE ?`,
`IN`-списки, `ORDER BY ULOWER(tasks.title)`, сравнение
`ULOWER(tasks.title) = ULOWER(?)` — без переписывания на нормализацию параметров.

Следствия, ради которых это делается:

- В схеме не появляется ни одной новой колонки и ни одной производной таблицы.
- Записи мимо Rust (откат на node, `restore.mjs`, ручная правка) физически не
  могут рассинхронизировать поиск: хранимого состояния нет, значение считается на
  чтении.
- Не нужны ни триггеры, ни догрузка при старте, ни проверка «не устарело ли».

Цена и границы:

| Что                             | Как закрыто                                                                                              |
| ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `unsafe` в проекте              | ровно один модуль `core::db::ulower`; в остальных крейтах `#![forbid(unsafe_code)]`                      |
| Версия `libsqlite3-sys`         | пин на версию, которую тянет `sqlx` (сейчас `^0.37`); `cargo tree -d` в пайплайне падает на дубле SQLite |
| Регистрация на каждой коннекции | единственный `after_connect`; забыть коннекцию нельзя, других путей к БД нет                             |
| Обновление `sqlx`               | `lock_handle` — единственное место, зависящее от версии; при мажорном апдейте проверяется первым         |

Таблица выше — всё, что нужно знать про `ULOWER`: остальной SQL переносится
дословно, включая `lower()` там, где node сам его использует.

## Миграции и откат на node

26 миграций схлопываются в одну:

- `0001_init.sql` — ровно финальная схема node, ни одной лишней колонки. В конце
  вставляет 26 node-имён в `schema_migrations` с `batch = 1`.

Дальше:

1. Своя история — в `_sqlx_migrations`, единственной новой таблице; node её не
   читает и не требует.
2. Старая node-база: если `schema_migrations` есть, а `_sqlx_migrations` нет,
   миграция `0001` помечается применённой с контрольной суммой, посчитанной из
   байтов встроенного файла (не вписанной руками).
3. Пока откат на node поддерживается, Rust-миграции только аддитивные.

Проверки приёмки:

- свежая база, созданная Rust: `pnpm migrate:status` — ноль ожидающих;
- `PRAGMA table_info` и `sqlite_master` свежей и унаследованной базы совпадают;
- node стартует на Rust-базе, читает и пишет, спеки node проходят;
- `POST /api/backup` до переключения и `rollback:node -RestoreBackup` возвращают
  снапшот.

## Этапы

Порядок задан так, чтобы каждая фаза заканчивалась проверяемым результатом.
Оценки — рабочие дни одного человека.

### 1. Захват контракта (3 дня)

Это определение «точной копии» и приёмочный тест для всего остального.

1. `scripts/parity/seed.mjs` — детерминированная база через node-операции.
2. `scripts/parity/capture.mjs` — снимает `tools/list`, ответы всех 55 операций,
   ошибочные кейсы, `/api/health`, форму SSE, набор медиа.
3. `scripts/parity/normalize.mjs` — правила обезличивания uuid, времени и путей
   в ответах, чтобы снапшоты были воспроизводимы.
4. `scripts/parity/compare.mjs` — гоняет те же запросы против Rust и диффит.
5. Снапшоты коммитятся в `tests/parity/fixtures/`.

Готово, когда: два прогона `capture` на node дают пустой diff, а `compare`
падает на заведомо испорченном ответе.

### 2. Каркас и база (9 дней)

1. Workspace, `rust-toolchain.toml`, `cargo sqlx prepare` и закоммиченный
   `.sqlx/`; сборка с `SQLX_OFFLINE=true`. Пин `libsqlite3-sys` под версию `sqlx`,
   проверка `cargo tree -d`.
2. `core`: конфиг с теми же env-переменными, пул, pragmas, `Tx`, `AppError`.
3. Миграция `0001`, baseline с вычисленной суммой, регистрация `ULOWER` в
   `after_connect`.
4. `/api/health`, `/media/*`, `/deleted/media/*`, `/api/backup`.
5. События: счётчик `seq`, подписчики, broadcast, heartbeat 15 с.
6. Бэкапы: daily/weekly/manual/auto, ретенция, `maybeAutoBackup` перед
   MCP-командами, `XBOCT_LOG_ACTIVITY_KEEP_DAYS`.
7. `cli`: `--port/--host/--data/--no-open/--portable/--version`, `instance.json`,
   проверка `/api/health`, `--version` без запуска сервера.

Готово, когда: сервер поднимается на копии рабочей базы, `/api/health` совпадает
с node, `migrate:status` показывает ноль ожидающих.

### 3. Задачи (5 дней)

`tasks_list`, `tasks_get`, фильтры и сортировки, `tasks_create`, `tasks_update`,
`tasks_move`, `tasks_batch`, `tasks_delete/restore/purge`, связи
(`blocks/relates_to/duplicates`), блокеры, ревизии, авто-закрытие эпика,
статистика. Здесь же — точная семантика `move`/`renumber` и поддерева эпика.

Готово, когда: `compare` зелёный по всем task-операциям, включая инвариант
уникальности `key` и монотонность номеров.

### 4. Остальные ресурсы (7 дней)

Проекты и префиксы, скоупы с dry-run отчётом удаления, словарь тегов и
инвентаризация, комментарии, вложения (запись, перемещение, purge, корзина,
проверка целостности), активность и её журнал, операции бэкапов и восстановления.

Готово, когда: `compare` зелёный по всей поверхности, вложения отдаются теми же
байтами и заголовками.

### 5. MCP (5 дней)

`rmcp` поверх `/mcp`: инструменты из реестра, два ресурса, шаблон
`xboct-log://attachment/{id}`, `attachments_read` с image-блоком, инструкции
сервера дословно, `isError` + `structuredContent`, strict-отказ с подсказкой
«Did you mean», уведомления после изменения вложений.

Готово, когда: `tools/list` совпадает со снапшотом байт в байт, клиент из
`~/.config` работает без правок.

### 6. Фронтенд на REST (5 дней)

1. REST-слой операций на сервере: маршруты `POST /api/<имя операции>` генерируются
   из реестра, тело — input, ответ — output, ошибки `{kind, message}` с
   400/404/409/500, заголовок `x-xboct-client` из запроса попадает в `Ctx`.
   `GET /api/openapi.json` — из `utoipa`; если `ToSchema` не справляется с
   `flatten` и `BTreeMap<Status, i64>`, схема собирается `schemars` и это
   отдельная задача в трекере.
2. Генерация `schema.d.ts`: бинарник пишет `openapi.json`,
   `openapi-typescript` — `src/lib/api/schema.d.ts`; `pnpm contract:check`
   перегенерирует и падает на `git diff --exit-code`.
3. Dev-контур: Vite-proxy `/api`, `/media`, `/deleted/media`, `/mcp` на
   `127.0.0.1:45881`; `scripts/dev.mjs` поднимает рядом
   `cargo run -p xboct-log-cli -- --port 45881 --no-open`, ждёт `/api/health`
   и только потом запускает Vite. БД и бэкапы остаются в `.dev` из env, флаг
   `--data` не передаётся. Зависимости `openapi-fetch` и `adapter-static`
   ставятся здесь.
4. Клиент на `openapi-fetch`: `src/lib/api/client.ts` забирает таймаут и
   ретраи у `src/lib/client/remote-fetch.ts`, `src/lib/api/*.ts` повторяют
   нынешние имена (`getProjects`, `createProject`, …), поэтому в сторах и
   компонентах меняется только путь импорта. Сторы, компоненты и SSE не
   переписываются. Ретрай — только на сетевом сбое: REST теперь POST, повтор
   HTTP-ошибки выполнил бы команду дважды. `tasks_list` получает дефолт
   `limit = 100`, ответы `serde_json::Value` приводятся к доменным типам на
   границе обёртки.
5. Переключение сборки и удаление старого слоя: `adapter-static` с
   `fallback: "index.html"` вместо `adapter-node`, `ssr = false` в корневом
   `+layout.ts`, без `experimental.remoteFunctions`. Удаление `src/lib/remote`,
   `src/routes/mcp/+server.ts`, `src/routes/api/**`, `src/routes/media/**` и их
   спек; `parity:seed` переезжает на скрипт без `#lib/remote`, фикстуры
   паритета остаются коммитнутыми. Переход на TanStack Query — не входит в
   переезд, отдельная задача в трекере.
6. Rust отдаёт собранный SPA с диска: `crates/server/src/static_files.rs`
   читает файлы, отдаёт `index.html` как fallback, `mime_guess` и
   cache-control. Папка по умолчанию — `build` рядом с exe, иначе `build` в
   рабочей директории; переопределяется `--web` и `XBOCT_LOG_WEB_DIR`.
   Пересборка Rust при изменении UI не нужна.

Готово, когда: `pnpm check` чист, в SPA не осталось ни одного ручного типа ответа,
все экраны работают на живом сервере.

### 7. Деплой, откат, приёмка (8 дней)

1. `scripts/deploy-rust.ps1`: сборка SPA и `cargo build --release --locked`,
   раскладка в `%USERPROFILE%\.xboct-log\app-rust`, бэкап через
   `POST /api/backup`, сохранение конфигурации NSSM, переключение, health-gate с
   автооткатом при неудаче.
2. `scripts/rollback-node.ps1 [-RestoreBackup <file>]`: возврат конфигурации
   сервиса из `node-service.json`, опциональное восстановление снапшота, старт и
   проверка здоровья.
3. `scripts/maintenance.ps1`: остановка, бэкап, прогон миграций node
   (`migrate.mjs apply`), `PRAGMA integrity_check` и `foreign_key_check`, старт.
   Это путь для случаев, когда откат — не просто деплой.
4. Состояние: `%LOCALAPPDATA%\xboct-log\deploy\current.json`
   (`{backend, version, path, switchedAt}`) и `node-service.json`.
5. Скрипты в `package.json`: `deploy:rust`, `rollback:node`, `maintain`.
6. Прогон на копии рабочей базы, затем на pet-инстансе. Work-инстанс остаётся на
   node: расширение передаёт `--port/--data` в `xboct-log.mjs`, но Rust-CLI
   принимает те же флаги, поэтому переезд возможен без правки расширения.

### 8. Юзкейсы на копии прода (4 дня)

Отдельно от снапшотов фазы 1: там синтетический сид, здесь — реальный объём и
реальные данные. Сценарии лежат в `tests/e2e/` и ходят только через внешнюю
границу: HTTP, SSE и MCP-клиент, никаких внутренних вызовов `core`.

1. Вход — копия продакшен-базы через `VACUUM INTO` с включённым WAL, а не
   `cp` файла; копия создаётся скриптом, а не руками.
2. Двойной прогон: те же сценарии против node и против Rust на одинаковых
   копиях. Сравниваются ответы и финальный `sqlite3 .dump` с обезличиванием
   uuid и времени — так ловятся побочные записи, которых нет в ответах
   (активность, ревизии, `key`, `updated_at`).
3. Сценарии по группам:
   - задачи: эпик и дети, авто-закрытие эпика, `renumber`, `move` между
     проектами и скоупами, `batch`, удаление/восстановление/purge;
   - поиск: `q_any` по всем пяти источникам, `title_exact`, `id_exact`,
     фильтры по тегам, скоупу, исполнителю, эпику, сортировки, пагинация,
     статистика;
   - связи и текст: `blocks`/`relates_to`/`duplicates`, история блокеров,
     комментарии, ревизии, словарь тегов и инвентаризация;
   - вложения: добавление, чтение, перемещение, корзина, восстановление, purge,
     `verify`, отдача байтов по `/media/*`;
   - служебное: бэкап и восстановление, журнал активности, SSE-событие на каждую
     команду, ошибки и `Did you mean`, вызовы из MCP-клиента.
4. Покрытие проверяется механически: `tests/e2e/coverage.mjs` сверяет список
   операций из реестра Rust с теми, что встретились в сценариях, и падает на
   непокрытой. Список не пишется руками и не может отстать.
5. Read-only обход SPA (Playwright): списки, фильтры, карточка задачи, вложения,
   журнал. Данные не меняются, гоняется на копии прода.

Готово, когда: все сценарии зелёные на копии рабочей базы, дамп после прогона
Rust совпадает с дампом после node, ни одна операция не осталась без сценария,
read-only обход SPA проходит без ошибок в консоли.

## Приёмка целиком

1. `pnpm test:parity` — зелёный на всех операциях, MCP и ошибках.
2. `ULOWER` совпадает с node на корпусе строк: кириллица, турецкая `İ`,
   финальная сигма, ASCII, пустая строка, `null`.
3. Спеки node портированы в `#[tokio::test]` для `core`; компонентные тесты
   Svelte остаются как есть.
4. Rust-база принимается node без миграций; node-база принимается Rust без миграций.
5. `pnpm test:e2e` — зелёный на копии прода: сценарии покрывают все операции,
   дамп после Rust совпадает с дампом после node.
6. Бэкап, восстановление и purge проходят на реальном объёме данных.
7. Переключение и откат отработаны на копии рабочей базы; после отката node
   пишет, Rust снова читает ту же базу.

## Риски

- `move`/`renumber` и авто-закрытие эпика — главный источник расхождений;
  закрываются только тестами паритета.
- Тексты strict-ошибок и инструкции MCP должны совпасть дословно, иначе
  настроенные клиенты увидят разницу. Сверка идёт по снапшотам.
- `unsafe` в модуле `ULOWER`: неверная сигнатура колбэка или деструктор дают UB.
  Модуль один, покрыт тестами, в остальных крейтах стоит `#![forbid(unsafe_code)]`.
- Дубль SQLite в дереве зависимостей после обновления `libsqlite3-sys` — ловится
  `cargo tree -d` в пайплайне.
- `lock_handle` — не публичный контракт, а деталь `sqlx`; мажорный апдейт может
  его изменить, и это первое, что проверяется при обновлении.
- Две реализации одного поведения (node и Rust) живут одновременно до полного
  переключения; любая правка node в этот период требует такой же правки в Rust.
- `sqlx` без живой БД собирается только в offline-режиме: забытый
  `cargo sqlx prepare` ломает деплой, поэтому это шаг пайплайна, а не привычка.
