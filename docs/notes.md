# Заметки: архитектура и эксплуатация

Про то, чего быстро не увидеть в коде. Что читается из кода — здесь не
повторяется.

## Карта кода

- `src/lib/server/*` — домен на neverthrow: возвращает `Result`, не бросает.
  `HttpError` появляется только на границе (`unwrap` для UI, `runOp`/тул для
  MCP).
- `src/lib/remote/*` — операции; `registry.ts` — единственный источник и для UI,
  и для `/mcp`, поэтому новая операция обязана попасть туда, иначе её не будет в
  MCP.
- `migrations/*.js` применяются на старте в `hooks.server.ts`: `getDb()` →
  `migrateDatabase()` → `ensureInbox()` → `startBackupScheduler()`.
- Импорт — через `#lib/...` (alias в `package.json` → `imports`), не `$lib`.

## Неочевидные инварианты

- **ID задачи — `PREFIX-NUMBER`** и меняется при переносе между проектами.
  `moveTask` — единственное место, где переписывается `id`; поддерево эпика
  переезжает целиком, а `scope_id` при переносе сбрасывается. Номера не
  переиспользуются (`task_number_high_water`). Soft-удаление тоже держит номер
  занятым.
- **Префикс проекта — верхний регистр, уникален без учёта регистра.**
  Уникальность держат триггеры в БД, а не приложение (`UNIQUE` в SQLite
  регистрозависим).
- **Беспроектных задач нет:** `tasks.project_id NOT NULL`, служебный `inbox`
  (`INB`) создаёт `ensureInbox`, архивировать его нельзя.
- **Резолв id** (`resolveTaskId`, `resolveEpicId`): только полный
  `PREFIX-NUMBER`, без учёта регистра. Голый номер отвергается — он уникален
  лишь внутри проекта. Эпик обязан быть эпиком того же проекта.
- **Блокеры** (`task_blocked_by`): `blocked_task_id` заблокирован
  `blocked_by_task_id`, блокер может быть из другого проекта. Self-блок и циклы
  (включая транзитивные) отвергаются, повторная связь — no-op. Закрывать
  заблокированную задачу можно; при закрытии/удалении блокера задача
  возвращается в `blocked_from_status` (если это был `open`/`in-progress`),
  иначе в `open`, — но только когда открытых блокеров не осталось. Статус
  `blocked` ставится руками и не выводится из списка блокеров. Причина внешней
  блокировки живёт в `blocked_reason`: одно строковое поле, только у `blocked`,
  очищается при выходе из статуса и при автоснятии.
- **Скоупы включаются неявно:** режим активен, если у проекта есть хоть один
  скоуп. «Без скоупа» — это `scope_id IS NULL`; удаление скоупа не трогает
  задачи.

## Эксплуатация (prod)

- **Prod** — артефакт вне git, служба NSSM `xboct-log`, порт `45881`,
  `HOST=0.0.0.0`. Прод-пути захардкожены только в `scripts/deploy.ps1`.
- **Деплой:** `pnpm run deploy`, не `pnpm deploy` (встроенная команда pnpm
  перехватывает имя). Скрипт держит постоянный worktree на `origin/main`,
  собирает, копирует артефакты и `.env` в прод-папку, затем перезапускает
  службу. Нет `.env` в worktree — падение до касания прода (fail-closed).
- **Серверные переменные `static: true`, их значения вшиваются в сборку.**
  Источник — `.env` в worktree на момент `pnpm build`. Менять
  `XBOCT_LOG_BACKUP_*` и прочее на сервере бессмысленно: нужна пересборка.
  Прод-миграции идут на старте, `scripts/migrate.mjs` — только dev (ходит в
  `XBOCT_LOG_DEV_DB`, `.env` не читает).
- **Схема запроса.** `adapter-node` без `PROTOCOL_HEADER` считает схему `https`
  и отбивает не-GET как cross-site (403). `scripts/start-prod.mjs` выставляет
  `PROTOCOL_HEADER=x-forwarded-proto` и `x-forwarded-proto: http` до импорта
  `handler.js`. Без этого падают все команды, а query работают.
- **Прод-`node_modules` — только runtime.** Собранный сервер импортирует
  `neverthrow`, `zod`, `@ku6epxboctuk/sqlite-up`, `mcp-handler` (+ peer
  `@modelcontextprotocol/server`); иконочные пакеты держатся в
  `devDependencies`.
- **Node ≥ 22.5** из-за `node:sqlite`. Bun не подходит.
- **Изоляция прод-путей** держится вручную: после правок путей гонять
  `git grep -n -E "xboct-log|build-wt|nssm"`. Прод-пути допустимы только в
  `deploy.ps1`.

## Бэкапы

- Четыре вида: `auto`, `daily`, `weekly`, `manual`; у каждого своя папка и
  prune.
- **Автоснимок** снимается в `runOp` до `op.handler`, только для MCP-команд: он
  фиксирует состояние до правки. Ошибка снимка не блокирует операцию
  (fail-open). Троттлинг двухуровневый — in-memory + mtime свежего файла, иначе
  рестарт или reload в dev плодил бы снимки.
- **Восстановление — только CLI** (`scripts/restore.mjs`): `node:sqlite` не
  умеет заливать файл в живой `DatabaseSync`, а `getDb()` держит синглтон.
  Скрипт отказывается работать при занятом порте, проверяет снимок
  (`integrity_check` + `schema_migrations`), сохраняет текущую БД в `manual/` и
  пишет атомарно (`.new` + rename). Путь: `--db` → `XBOCT_LOG_DB` → `.env` рядом
  со скриптом.
- Тесты пишут в `.dev/test-backups` (`vite.config.ts`, режим `test`), иначе
  дефолт указывает на прод-папку.
- **Старый снимок на новом коде безопасен** (миграции догонят на старте),
  обратное — нет.

## Разработка

- `pnpm dev` (`scripts/dev.mjs`) всегда идёт на `XBOCT_LOG_DEV_DB`
  (`.dev/dev.db`), игнорируя `XBOCT_LOG_DB`, отключает бэкапы и уводит их в
  `.dev/backups`. `pnpm dev:vite` — без изоляции, требует `XBOCT_LOG_DB`.
- `pnpm dev:seed` кладёт свежий снимок из `.dev/seed/` в `.dev/dev.db`; прод не
  читается, снимок кладёт человек.
- У `XBOCT_LOG_DB` нет значения по умолчанию: без неё сборка и сервер падают.

## Расширение VS Code

`vscode-extension/` — тонкий клиент: `WebviewPanel` с `<iframe>` на прод-URL.

- **Только `127.0.0.1`/`localhost`:** из `vscode-webview://` http-iframe
  разрешён лишь для potentially-trustworthy origin, LAN-IP упадёт как mixed
  content.
- **Тема не наследуется** (кросс-доменный iframe): передаётся через `?theme=` и
  `postMessage` при смене.
- **`retainContextWhenHidden: true`** обязателен, иначе переключение вкладки
  перезагружает SPA.

## MCP и сеть

- `/mcp` — Streamable HTTP в том же процессе. Токена нет сознательно: прод уже
  открыт в сети без аутентификации, токен на одном эндпоинте дал бы ложное
  чувство защиты.
- Прод слушает `0.0.0.0:45881` без входа; изоляция — правило Windows Firewall на
  нужную подсеть/IP.
